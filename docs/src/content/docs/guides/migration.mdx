In 1.0.0rc4, every route of the node's API is a method generated from core's
OpenAPI document: `client.<group>.<method>(...)`. The method per route that
1.0.0rc1 to rc3 had on `Client` is gone (rc3 deprecated it), and v1's client
went in 1.0.0rc1.

## From 1.0.0rc3 (and rc1, rc2)

1. **Install rc4**: `pip install calimero-client-py==1.0.0rc4`. It adds two
   dependencies, `httpx` and `attrs`.
2. **Find the replacement** of each call in the table below. On rc3, the
   `DeprecationWarning` each old method raised names it too:
   `python -W error::DeprecationWarning` turns every remaining call into an
   error.
3. **Rewrite the arguments as keywords** named as the route names them
   (snake case). A dict of options becomes keyword arguments:

   ```python
   # rc3
   key_id, key = client.create_api_key({"readOnly": True}, passkey)
   # rc4
   made = client.auth.apikey_create(read_only=True, confirm=passkey)
   key_id, key = made.key_id, made.key
   ```

4. **Pass passkeys as `confirm=`**, or set one for the client with
   `client.use_passkey(passkey)`. The operator key answers by itself, as
   before (`use_operator_key`), and per call with `operator_proof=`.
5. **Read the answer as a model** (`client.orgs.create(name=...).org_id`,
   `.to_dict()` for the JSON). To keep the dicts rc3 returned, call the same
   method under `client.json`: `client.json.orgs.create(name=...)`
   returns `{"orgId": ...}`. Some rc3 methods unwrapped answers: `create_org`
   returned the id where `orgs.create` answers `{orgId}`, and `list_apps`
   returned the list where `apps.list` answers `{apps}`.
6. **Check the fields you relied on being sent.** rc3 always sent some fields
   that rc4 sends only when you give them (`call`'s `args`, `view`'s
   `consistency`, `invite`'s `ttlSecs`); the node reads an absent field as its
   default. `view(..., stale=True, min_index=n)` is
   `apps.view(..., consistency="stale", min_index=n)`, and
   `ops_approve_release(v, withdraw=True)` is
   `ops.release(version=v, approved=False)`.

What is not a route stays as it was: `connect`, the credentials
(`use_api_key`, `use_session`, `session`, `refresh`, `use_operator_key`), the
passkey ceremonies (`sign_up`, `sign_in`, `add_passkey`,
`start_account_recovery`, `finish_account_recovery`, `start_recovery`), the
streams (`events`, `presence_stream`), `verify_app_cluster`, `attestation`,
the key helpers and the calls on any path (`get`, `post`, `post_confirmed`,
...). rc4 adds `use_passkey` and `use_operator_signer`.

`POST /apps`' `confirmMethods` is not in core's document; send it with
`client.post("apps", {...})`.

## 1.0.0-rc.3

## From 0.9 (the v1 client)

0.9 was the client for v1's peer-to-peer node, which Calimero 1.0 replaced
with attested clusters. Nothing of it carries over unchanged: connect with
`Client(base_url, ...)` or `Client.connect(cluster)`, sign in with a passkey or
an API key, then use the groups.

| 0.9 | 1.0.0rc4 |
| --- | --- |
| `create_connection`, `ConnectionInfo` | `Client(base_url, ...)`, `Client.connect(cluster)` |
| `create_client`, v1's `Client` | `Client` and its groups |
| `install_application`, `install_dev_application` | `client.packages.bundle_put(body=wasm)`, `client.packages.upload(body=mpk)`, `client.packages.install(...)` |
| `create_context` | `client.apps.create(...)` |
| `list_contexts`, `get_context` | `client.apps.list()`, `client.apps.get(app=...)` |
| `execute_function` | `client.apps.call(...)` (writes), `client.apps.view(...)` (reads) |
| `update_context_application` | `client.apps.upgrade(...)` |
| `upload_blob`, `download_blob` | `client.apps.blob_upload(...)`, `client.apps.blob_download(...)` (scoped to an app) |
| Namespaces | Organizations: `client.orgs.create`, `get`, `set_member`, `remove_member`, `capabilities`, `invite_create`, `invite_redeem` |
| Groups | Teams: `client.orgs.team_create`, `team_get`, `team_update`, `team_delete`, `team_set_member`, `team_remove_member` |
| `AuthMode`, `JwtToken`, the token cache | `sign_up` / `sign_in` with a passkey, `use_session`, `refresh`, or `use_api_key` (sessions are not cached on disk) |
| `TeePolicy` | `Client`'s `tee_profiles`, `min_release`, `allow_debug_profiles`, `allow_mock`, `app_hash` |
| `sealed=True` | Always on |
| `sign_warrant`, `sign_request` | None: a cluster authenticates the caller's session or API key |
| `ClientError` | `CloudError(message, status, code, details)` |
| The `calimero-client-py` command | None: `meroctl` is Calimero 1.0's command line |

Context identities, peer counts, syncing, device pairing, intent relays and
group upgrades have no equivalent: they were properties of the peer-to-peer
node.
